# Uptime Kuma 2.5.8 - Notification providers

Machine-readable companion: `spec/notification-providers.json` (108 providers, 433 form fields, generated by scanning
`src/components/notifications/*.vue`, `src/components/notifications/index.js`, `src/components/NotificationDialog.vue`,
`server/notification-providers/*.js`).

## 1. Notification object and socket calls

A notification is a free-form JSON object. The web UI builds it in `NotificationDialog.vue` and each provider form binds its
inputs to `$parent.notification.<field>`. The whole object is persisted as the `config` text column (`server/notification.js:273-301`);
`name` and `isDefault` are mirrored into the `name` / `is_default` columns.

Common keys:

| Key | Type | Notes |
|---|---|---|
| `name` | string, required | default `"My <Label> Alert (N)"` (`NotificationDialog.vue:511-521`, `en.json: defaultNotificationName`) |
| `type` | string, required | provider id = key of `NotificationFormList` (`src/components/notifications/index.js:114-223`) = server `name` property (`server/notification.js:122-247`; both lists match 1:1 in 2.5.8). UI default for a new notification: `"telegram"` |
| `isDefault` | boolean | "Default enabled": pre-selected for new monitors |
| `applyExisting` | boolean | one-shot: attach to all existing monitors on save; server resets it to `false` before storing (`server/notification.js:286-288`) |
| `active` | boolean | DB column only (default true); not in the dialog |
| `id` | number | present in `notificationList` rows (column), **not** inside `config` |

Socket events (`server/server.js:1567-1635`):

- `addNotification(notification, notificationID | null, cb)` -> `{ok:true, msg:"Saved.", msgi18n:true, id}`; then `notificationList` is pushed. Pass the existing id to edit.
- `deleteNotification(notificationID, cb)` -> `{ok:true, msg:"successDeleted", msgi18n:true}`.
- `testNotification(notification, cb)` -> `Notification.send(notification, notification.name + " Testing")` with `monitorJSON = null`, `heartbeatJSON = null`; ack `{ok:true, msg:"Sent Successfully."}` (provider-specific ok text) or `{ok:false, msg}`. The object does not need to be saved first.
- `checkApprise(cb)` -> bare boolean.
- S->C `notificationList`: `[{id, name, active: boolean, user_id, is_default: 0|1, config: "<json string>", isDefault: boolean}]` (`server/client.js:18-36`).

Editing in the UI: `notification = JSON.parse(row.config); notification.applyExisting = false` (`NotificationDialog.vue:431-445`).

## 2. Message generation (what providers receive)

`Monitor.sendNotification` (`server/model/monitor.js:1457-1524`):

- `msg = "[" + monitor.name + "] [" + text + "] " + bean.msg` where `text` is `"✅ Up"` for UP and `"🔴 Down"` otherwise (`:1461-1468`).
  Examples: `[My Site] [🔴 Down] timeout of 48000ms exceeded`, `[My Site] [✅ Up] 200 - OK`.
- `monitorJSON = monitor.toJSON(preloadData, includeSensitiveData=false)` (no headers/body/credentials; has `tags`).
- `heartbeatJSON = bean.toJSONAsync({decodeResponse:true})` plus `msg` defaulted to `"N/A"`, `timezone`, `timezoneOffset`, `localDateTime` (`"YYYY-MM-DD HH:mm:ss"` in server tz), and on UP `lastDownTime` (time of the last important DOWN beat) (`:1470-1508`).
- Certificate expiry notifications use `Notification.send(config, "[<name>][<url>] <certType> certificate <CN> will expire in <days> days")` with **no** monitor/heartbeat JSON (`:1549-1585`); domain expiry similar (`server/model/domain_expiry.js`).
- Notifications are sent when `isImportantForNotification` is true (first beat only if DOWN; UP->DOWN; DOWN->UP; PENDING->DOWN; MAINTENANCE->DOWN) and again every `resendInterval` consecutive DOWN beats (`:970-1007`).

### Liquid templates

Providers with "custom message/template" fields render them with `NotificationProvider.renderTemplate` (`server/notification-providers/notification-provider.js:75-113`, liquidjs with partials disabled). Context variables:

| Variable | Value |
|---|---|
| `msg` | the default message above |
| `name` | monitor name (`"Monitor Name not available"` when testing) |
| `status` | `"🔴 Down"` / `"✅ Up"` / `"⚠️ Test"` |
| `hostnameOrURL` | `extractAddress(monitorJSON)` (`:32-65`): push -> `"Heartbeat"`; ping/dns -> hostname; port/gamedig/steam -> `host:port`; globalping -> hostname or url by subtype; default -> url unless it is `https://`/`http://`/empty |
| `monitorJSON` | the non-sensitive monitor JSON or `null` |
| `heartbeatJSON` | the heartbeat JSON (see above) or `null` |
| `NAME`, `STATUS`, `HOSTNAME_OR_URL` | v1 aliases |

Example: `{{ name }} is {{ status }} at {{ heartbeatJSON.localDateTime }} ({{ heartbeatJSON.msg }})`.

### Outbound proxy

All axios-based providers call `getAxiosConfigWithProxy` which honours env `NOTIFICATION_PROXY` / `notification_proxy` (http/https/socks) (`:175-196`). Errors are normalised by `throwGeneralAxiosError` into `"<message> (code=...) (HTTP <status> <text>) <body>"` (`:121-168`).

## 3. `ntfy` in detail

Form (`src/components/notifications/Ntfy.vue`) and server (`server/notification-providers/ntfy.js`):

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `ntfytopic` | text | yes | - | topic name only |
| `ntfyserverurl` | text | yes | `"https://ntfy.sh"` (set in `mounted()` when `ntfyPriority` is undefined, `:168-172`) | **Server root URL** without topic. The provider POSTs JSON to exactly this URL (`ntfy.js:60,129`) with `topic` in the body (ntfy "publish as JSON" mode). A base path is allowed as long as it is the ntfy root. |
| `ntfyPriority` | number 1..5 | yes | `5` | priority for UP / test / other |
| `ntfyPriorityDown` | number 1..5 | yes | `5` | priority for DOWN; if falsy the server uses `min(ntfyPriority + 1, 5)` (`:71`) |
| `ntfyAuthenticationMethod` | select | no | `"none"` (or `"usernamePassword"` if a legacy `ntfyusername` exists, `:180-186`) | `"none"` \| `"usernamePassword"` \| `"accessToken"` |
| `ntfyusername` | text | no | - | shown for `usernamePassword` -> `Authorization: Basic base64(user:pass)` (`ntfy.js:16-21`) |
| `ntfypassword` | password | no | - | with the above |
| `ntfyaccesstoken` | password | no | - | shown for `accessToken` -> `Authorization: Bearer <token>` (`:22-26`) |
| `ntfyIcon` | text (URL) | no | - | always shown; sent as `icon` in the JSON body for monitor events only (`:125-127`) |
| `ntfyCall` | text | no | - | always shown; placeholder `yes or +12223334444`; sent as HTTP header `X-Call` (`:27-29`) |
| `ntfyUseTemplate` | checkbox | no | `hasTitle \|\| hasMessage` for legacy configs (`:188-193`) | enables the two template fields |
| `ntfyCustomTitle` | Liquid template (single line) | no | - | overrides `title` when non-empty and `ntfyUseTemplate` |
| `ntfyCustomMessage` | Liquid template (multi line) | no | - | overrides `message` when non-empty and `ntfyUseTemplate` |

Request built by `ntfy.js`:

- Test / certificate (no `heartbeatJSON`, `:35-62`): `POST <ntfyserverurl>` JSON `{ topic, title: "<monitor name or topic> [Uptime-Kuma]", message: msg, priority: ntfyPriority, tags: ["test_tube"] }` (title/message replaced by templates if enabled). No `icon`, no `actions`.
- Monitor event (`:63-131`):
  ```json
  {
    "topic": "<ntfytopic>",
    "message": "<heartbeatJSON.msg or rendered ntfyCustomMessage>",
    "priority": <DOWN ? (ntfyPriorityDown || min(ntfyPriority+1,5)) : (ntfyPriority || 4)>,
    "title": "<monitor.name> <Down|Up|unknown> [Uptime-Kuma]  (or rendered ntfyCustomTitle)",
    "tags": ["red_circle" | "green_circle", "<tagName>" | "<tagName>: <value>" ...],
    "actions": [ { "action": "view", "label": "Open <monitor.name>", "url": "<monitor.url>" } ],   // only if monitor.url set and != "https://"
    "icon": "<ntfyIcon>"                                                                               // only if set
  }
  ```
  Monitor tags are appended to `tags` (`:79-88`). Headers: `Authorization` per auth method, `X-Call` if `ntfyCall`.
- Success message returned to `testNotification`: `"Sent Successfully."`.

## 4. `webhook` in detail

Form (`src/components/notifications/Webhook.vue`) and server (`server/notification-providers/webhook.js`):

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `webhookURL` | url (`https?://.+`) | yes | - | |
| `httpMethod` | select `"post"` \| `"get"` | no | `"post"` (set in `mounted()` when undefined, `Webhook.vue:108-112`) | server lower-cases it, missing -> post (`webhook.js:15`) |
| `webhookContentType` | select | yes (when `httpMethod === "post"`) | - (UI shows no preselection; legacy configs may lack it -> JSON) | `"json"` \| `"form-data"` \| `"custom"` |
| `webhookCustomBody` | Liquid template (multi line) | yes when `custom` | - | shown when `httpMethod === "post" && webhookContentType === "custom"`. Placeholder example: `{"Title": "Uptime Kuma Alert{% if monitorJSON %} - {{ monitorJSON['name'] }}{% endif %}", "Body": "{{ msg }}"}` |
| `webhookAdditionalHeaders` | textarea (JSON object string) | yes when the "additional headers" switch is on | - | UI toggle `showAdditionalHeadersField` defaults to `webhookAdditionalHeaders != null`; placeholder `{"Authorization": "Authorization Token"}`. Server: `JSON.parse` and merge into request headers; invalid JSON -> error `"Additional Headers is not a valid JSON"` (`webhook.js:47-56`). Applies to **all** methods/content types. To disable, store `null`/omit (an empty string is falsy and ignored too). |

Request built by `webhook.js:11-70`:

- `httpMethod === "get"`: `GET <webhookURL>?msg=<msg>&heartbeat=<JSON string>&monitor=<JSON string>` (`heartbeat`/`monitor` only when non-null) (`:26-37, 60-61`).
- POST + `webhookContentType` `"json"` or anything else/unset: `POST <webhookURL>` with axios default JSON body
  `{ "heartbeat": heartbeatJSON | null, "monitor": monitorJSON | null, "msg": "<msg>" }` (`Content-Type: application/json`).
- POST + `"form-data"`: `multipart/form-data` with a single part `data` = `JSON.stringify({heartbeat, monitor, msg})` (`:38-42`).
- POST + `"custom"`: body = `renderTemplate(webhookCustomBody, msg, monitorJSON, heartbeatJSON)` as a **string**; axios sends it as `application/x-www-form-urlencoded` by default unless `webhookAdditionalHeaders` sets `Content-Type` (e.g. `{"Content-Type":"application/json"}`) (`:43-45`). Template variables: `msg`, `name`, `status`, `hostnameOrURL`, `monitorJSON`, `heartbeatJSON` (see section 2).
- Additional headers merged last; proxy env honoured. Success: `"Sent Successfully."`.

So yes: 2.5.8 supports a custom Liquid body (`webhookContentType: "custom"`, `webhookCustomBody`) and extra headers (`webhookAdditionalHeaders`, JSON string) for the webhook provider.
